当前技术架构与实现机制

解释这个项目如何把遗留代码转成可追溯、可确认、可导出的业务知识：它解决的是什么问题、每一步由什么组件完成，以及三个产品如何围绕同一内核运行。

01 · THE PROBLEM

项目要解决的不是“代码解释”，而是业务知识失联

遗留系统中真正稀缺的往往不是代码文件，而是“为什么这样做”的业务知识：模块边界、业务规则、数据影响、流程例外与责任口径。代码存在，但知识无法被业务人员直接验证，也无法稳定复用到重构、迁移或交付中。

输入问题

代码很大，人工无法全读

类、方法、SQL、接口和调用关系分散在仓库中。仅靠关键词或通读，容易遗漏入口、跨模块调用与数据读写。

可信问题

纯模型总结不可审计

模型可以写出流畅说明，但如果没有文件、行号、方法和表等证据，团队无法判断结论是否真实，也无法定位修正。

交付问题

技术结论无法直接变成业务资产

项目需要业务域、规则、流程、数据和验收材料；这些成果必须标示来源、可信度和人工确认状态。

设计原则：先事实，后解释；先约束，后生成

原则当前实现方式避免的问题
确定性优先扫描器先解析 Java 代码，建立模块、类、方法、入口、调用边、SQL 与表等结构化记录。把“模型看到的上下文”变成可检查的代码事实，而非整库自由阅读。
语义受约束云端模型输出必须是 JSON，并经本地 schema 校验；Agent Native 必须按固定 contract 导入。自由文本不可消费、字段漂移和模型编造结构。
结论带证据规则关联文件、行号、方法和代码片段；Agent Native 在导入时逐条验证证据属于当前完成扫描。无法追溯、跨项目引用或伪造证据。
人工是正式边界确认、修改、废弃动作写入审计记录；正式文档只选取已确认或已修改的知识。把未核实的 AI 推断误当作业务事实。
02 · CORE ARCHITECTURE

一条闭环，两类图谱，三个独立入口

无论使用 Web、CLI 还是 Agent Skills，最终都进入同一个 core/ 内核。内核将代码事实与业务语义分开保存，再通过确认审计把“推断”与“已知”分开。

代码输入本地目录、ZIP、Git
→
确定性扫描解析、调用、SQL、表、入口
→
代码事实图谱可定位到文件与行号
→
业务语义图谱域、对象、规则、流程
→
确认与导出审计、正式文档、规格包

两类图谱分别解决什么问题

代码事实图谱：回答“代码里有什么”

其来源是解析器而不是模型。主要实体包括 modules、code_objects、call_edges、api_endpoints、data_tables 与 sql_operations。

它的价值是可复现：同一版本代码重新扫描，会得到相同类型的结构事实；解析失败或动态调用不会被伪装成确定结论。

业务语义图谱：回答“这些代码在做什么业务”

在事实图谱之上保存 business_domains、business_objects、business_rules、business_flows、主线与待确认项。

它的价值是可理解：技术调用被翻译为业务对象、动作与规则；但每个结论都要保留其证据、可信度与确认状态。

共享内核与产品外壳的关系

Web 工作台 ─┐ CLI ─┼─> core/（扫描 / 图谱 / 语义 / 确认 / 文档） ─> SQLite 或 PostgreSQL Agent Skills ─┘ core/ 不是第四个产品，而是三种分发形态共同安装或调用的运行时。 产品可以单独运行；只有希望彼此看到同一项目结果时，才显式连接到同一个 PostgreSQL。
为什么不直接使用图数据库？当前 MVP 使用 SQLAlchemy 管理 SQLite / PostgreSQL，调用关系与 SQL 读写关系以边表保存。这样减少部署复杂度，同时满足按项目、按扫描版本查询局部关系图的需要。
03 · THREE INDEPENDENT PRODUCTS

三个产品共享能力，但服务不同的工作场景

“三产品”不是同一个应用的三个页面，而是三个可独立安装、独立部署、独立使用的入口。它们选择不同交互方式，但调用的是同一套事实、语义与文档能力。

产品实际组成使用者与入口如何独立运行与其他产品的关系
Web 工作台Vue 3 前端、Nginx、FastAPI API、PostgreSQL Compose 部署。业务、产品、实施、交付人员通过浏览器导入代码、查看结果、确认规则与下载文档。Docker Compose 可启动前端、API 与内置 PostgreSQL；不需要安装 CLI 或 Skills。默认使用自己的数据卷。需要和 CLI/Skills 共用结果时，改为连接同一个受保护 PostgreSQL。
CLIPython wheel，命令入口为 c2b。开发、架构、运维、CI 和脚本用户；适合批量、定时或无人值守执行。Python 3.11+ 即可；默认 SQLite，生产可通过 C2B_DB_URL 切换 PostgreSQL。完整功能入口；可以只用 CLI 完成扫描、语义、确认后的文档导出。
Agent Skills面向 Codex、Claude Code 等宿主的技能说明、安装脚本与内置 wheel。希望通过自然语言驱动分析，同时保留扫描与证据约束的 Agent 用户。安装 Skill 与 wheel 后运行；不需要 Web，也不要求单独安装 CLI。默认使用当前 Agent 进行首轮语义还原；通过底层 c2b 执行扫描和入库。

同一问题在三个产品中的使用方式

Web：本地评审

“上传仓库 → 浏览图谱 → 标注 → 确认/修改规则 → 导出文档”。重点是可视化、单团队评审和人工确认；当前不内置登录、角色权限或客户隔离。

CLI：工程自动化

“scan → label 或 Agent Native 导入 → docs → evaluate”。重点是可复跑、可脚本化与图谱回归接入。

Skills：对话编排

“自然语言请求 → 技能按阶段调用 core → 当前 Agent 解释与归纳 → 校验入库”。重点是不让 Agent 跳过扫描或直接凭空写结论。

04 · DETERMINISTIC SCAN

第一阶段：把仓库变成可验证的代码事实

扫描入口是 scanner.service.scan_project()，实际编排由 scanner.graph.Scanner 完成。它不调用 LLM，目标是建立后续所有推理的“证据底座”。

扫描管线的实际顺序

阶段当前实现产出与意义
1. 创建扫描创建 Project 与一条 Scan 记录；Web 可复用已创建项目，CLI 可新建项目。所有事实与语义都归属到特定项目、特定扫描版本，避免跨项目混写。
2. Probe 探测统计文件、代码行数、模块明细与规模档位；扫描状态进入 PROBING。判断是否需要按模块分片，生成扫描规模和覆盖范围说明。
3. 分片计划规模较大时按照模块形成分片，并为每片创建 scan_tasks 记录。当前代码仍由单进程顺序处理，但已经保留任务状态与未来并行化所需的数据结构。
4. Java 解析tree-sitter 提取包、类、方法、注解、注释、行号、字符串、调用表达式与入口标记。写入模块与代码对象；代码对象保留 file_path、起止行、签名与注解。
5. 调用解析用内存中的“类 + 方法 + 参数个数”索引解析调用目标。写入 call_edges。无法可靠解析的目标标记为 UNKNOWN，而不是猜测静态边。
6. SQL / 表提取从 Java 字符串、MyBatis XML 与 .sql 中提取语句；SQLGlot 解析读写表和字段，动态 SQL 或解析失败时使用粗粒度表名提取并降低可信度。写入 data_tables 与 sql_operations；Java 字符串可关联宿主方法，XML 当前仍是 statement/table 级证据。
7. 合并与完成所有解析中间结果先写入 JSONL 临时文件，再统一合并落库；成功后扫描状态为 DONE。避免边解析边写入造成半成品；异常时标记 FAILED 并记录错误摘要。

“确定性”不等于“无边界”

项目明确保守的地方：动态调用、反射、模板 SQL 或无法唯一定位的调用不会伪造成准确关系；相应记录会有 UNKNOWN 或较低可信度。
当前范围：深度解析以 Java 为主。架构文档曾描述过的前端路由、MQ、DDL 等扩展能力并不代表全部已经在当前扫描器中完整实现。
扫描完成后，数据库中已经有足以回答以下问题的“硬事实”： - 这个项目有多少模块、文件、类、方法？ - 哪些方法被识别为入口，位于哪个文件哪一行？ - 某方法调用了什么；哪些调用无法可靠解析？ - 哪段 SQL 在读写哪张表，它位于哪个方法/文件？ 但扫描器不会声称“这段代码就是订单审批规则”。这一步交给下一阶段的语义处理。
05 · SEMANTIC LAYER

第二阶段：把事实翻译成业务语言，但不放弃约束

语义层的职责是从模块、方法、入口、调用和数据线索中归纳业务域、对象、规则、流程与主线。当前项目提供两条路径：服务端可调用的云端 Provider，以及由当前编码 Agent 完成的 Agent Native 路径。

路径 A：云端 Provider（适合 Web、CLI 自动化）

事实图谱选材模块、候选方法、表、调用链
→
LLMClient统一协议与缓存
→
结构化 JSONSchema 校验
→
语义表落库一次提交，保留人工决定
组件 / 规则它具体做什么
LLMClient支持 openai_compatible 与 anthropic 两种协议。前者请求 /chat/completions；后者请求 /v1/messages。不对任意自定义 URL 猜测协议。
结构化输出提示中附带字段要求，本地再校验 JSON 的类型、必填字段、枚举和不允许的附加字段。兼容端即使返回 Markdown fence，也会先提取 JSON 再校验。
安全与运行控制外部 URL 通过出站地址校验；默认限制不安全地址。请求使用超时、重试、用量计数和基于输入指纹的本地缓存。
语义编排先识别业务域，再挑选更可能含业务语义的方法，随后生成规则、对象、流程与主线。重标时保留已经确认、修改或废弃的人为决定。

路径 B：Agent Native（适合 Skills、交互式 CLI）

当前 Agent 的会话不能被 Web 后台任务可靠继承，因此项目没有把 Agent “伪装成一个 HTTP Provider”。取而代之的是显式的导出—分析—校验—导入桥接：

c2b scan /path/to/repo --name 项目A c2b export-evidence 1 --output evidence.json c2b agent-schema > semantic-result.json # 当前 Codex / Claude Code 结合 evidence.json 与源码填写 semantic-result.json c2b import-semantic 1 --input semantic-result.json

导出的不只是提示词

export-evidence 从最近一次完成扫描中导出模块、方法、入口、接口、数据表和每个方法的文件、行号、签名、注释等事实。它明确提示 Agent：规则必须引用这些方法范围内的证据。

导入不是直接写数据库

import-semantic 检查 contract 版本、未知字段、业务域引用、字段类型、规则证据文件、起止行与方法归属。任一规则不合法，整个导入失败并回滚。

Agent Native 的保护点当前行为
只允许完成扫描后的项目导入没有 DONE 状态的扫描会被拒绝，避免用不完整图谱制造语义。
规则证据必须可定位规则的文件与 [起始行, 结束行] 必须落在本次扫描提取出的某个方法内部；如果提供 source_method，它也必须与证据方法一致。
一次性事务先完整校验 payload，再创建域、对象、规则、流程与问题；任何异常都会回滚，不留下半套业务知识。
人工作品不会被覆盖已确认、已修改与已废弃的规则被保留；机器生成的未确认内容才会被新结果替换。
关键区别：Agent Native 解决“用户已经有一个强大的当前 Agent，为什么还要配置另一套模型 Key”的问题；云端 Provider 解决“Web 后台、CI、批处理需要无人值守稳定调用”的问题。两者输出进入同一业务知识模型，但运行边界不同。
06 · DATA, TRUST & DOCUMENTS

第三阶段：用数据模型和确认审计决定什么可以被相信

C2B 不生成一个含义模糊的“总可信分”。数据库把静态证据、R0-R3 运行验证、AI 可信度和人工确认状态分别保存，文档导出时再按状态过滤。

核心数据关系

projects └─ scans（每次扫描的状态、元数据与统计） ├─ modules / code_objects / call_edges ├─ api_endpoints / data_tables / sql_operations ├─ business_domains / business_objects / business_rules / business_flows ├─ runtime_evidence / questions / confirmations / documents └─ scan_tasks / label_jobs（任务过程记录）

从 AI 推断到正式事实的状态机

AI 识别尚未被人核实
→
已确认业务或技术人员认可
→
正式文档可作为交付依据
↘
已修改 / 已废弃保留审计与原因
对象确认机制为什么重要
业务规则状态包含 AI 识别、已确认、已修改、已废弃、冲突；确认 API 保存用户、动作、修改前后内容与扫描版本。业务规则最容易被错误理解，且最需要留下“谁在何时按什么口径确认”的痕迹。
业务域、对象、流程有对应确认标记；正式导出时默认只选取已确认项。防止尚在讨论的域划分和流程推断进入最终材料。
运行证据规则、流程和推演可分别记录 R1 测试、R2 受控/预发布、R3 生产证据；无记录派生为 R0。R 等级不会修改 AI 可信度、V 静态证据或人工确认状态，避免不同含义被混算。
文档documents._gather() 默认排除未确认语义；只有显式 --draft 才会包含 AI 未确认内容和主线。把“内部探索材料”与“正式交付材料”分开，是项目最重要的信任边界。
数据库选择：开发或单机 CLI 使用 SQLite 即可；Web Compose 和跨产品协同时使用 PostgreSQL。init_db() 通过 SQLAlchemy 建表，并运行项目内的幂等增量迁移；当前没有引入 Alembic。
07 · WEB & RUNTIME IMPLEMENTATION

Web 是一个可视化入口，不是另一套业务引擎

Web 工作台的后端直接复用 core/ 的扫描、语义、确认和文档模块。前端负责呈现和操作；FastAPI 负责 API、任务调度、文件/Git 导入与安全边界。

Web 请求从上传到结果的路径

浏览器上传 ZIP / 提交 Git URL → POST /api/projects/import → 校验“二选一”输入、大小、压缩包安全或 Git 出站地址 → 为项目创建安全的本地存储目录；ZIP 解压完成，Git 在后台克隆 → 项目进入“待扫描”，用户核对后 POST /api/projects/{id}/scan → 后台线程调用 scan_project(...) → Scanner 落库并更新扫描状态 → 前端按项目查询概览、模块、规则、流程、数据与文档

当前 Web 的关键实现选择

部分实际技术与行为含义
前端Vue 3 + Vite + Element Plus；Compose 中由 Nginx 托管构建产物。负责工作台交互与图谱呈现，不承载扫描与模型逻辑。
APIFastAPI，路由位于 core/src/c2b/api/routes.py。项目导入、查询、确认、文档、任务状态等能力都通过 REST API 暴露。
后台任务使用进程内 threading.Thread，并通过 label_jobs 的部分唯一索引确保同一项目只有一个运行中的标注任务。适合当前 MVP；不是 Celery / Redis 分布式队列。
鉴权本地默认零配置；设置 C2B_API_TOKEN 后，API 接受 Bearer 或 X-C2B-Token。这是服务入口令牌，不是用户登录/角色权限/客户隔离；远程部署仍应由 HTTPS、身份认证和反向代理保护。
部署Compose 启动 PostgreSQL、API、Nginx；默认仅将前端绑定在 127.0.0.1:8080。默认不直接暴露到公网，远程访问需要部署者显式配置安全边界。

08 · CURRENT BOUNDARIES

当前已实现什么，哪些仍是演进方向

理解当前项目时，必须把“设计目标”与“已经落到代码中的能力”分开。下表按当前代码和 README 的实现基线整理。

Embedding 向量 RAG非当前主路径当前问答以有上限的图谱关键词检索为主，不以向量检索作为事实依据。

把项目放到实际工作中，建议这样理解

  1. 扫描回答“系统客观上有什么”。它能给出模块、入口、方法、调用、SQL、表及定位证据。
  2. 语义回答“这些结构可能表达什么业务”。模型和 Agent 帮助把技术结构转译成业务语言，但输出必须受 schema 和证据约束。
  3. 确认回答“哪些结论可以当作项目事实”。人工确认让交付物脱离模型的不确定性，成为可追责、可回溯的知识资产。
  4. 三个产品回答“团队以什么方式使用这套能力”。浏览器协作选 Web，工程自动化选 CLI，已使用编码 Agent 的团队选 Skills。
最终总结：Code2Business 的真正产品能力，不是“AI 解释代码”，而是把遗留代码分析过程拆成可验证、可审计、可协作的知识生产流水线。确定性扫描提供底座，语义能力提高理解速度，人工确认建立最终信任边界，Web / CLI / Skills 则让不同角色以合适的方式进入这条流水线。v0.3.0 增加的 macOS Desktop 是 Web 工作台的本地优先分发形态，复用同一 Core，不构成第四套分析逻辑。
