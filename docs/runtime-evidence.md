# 运行证据（R0-R3）设计与使用说明

> 实现版本：C2B v0.2.0（2026-08-09）
> 当前范围：本地单团队，支持人工录入和审计；不含 OpenTelemetry、APM 或日志平台自动采集

## 1. 为什么单独建立 R 维度

C2B 中有四种含义不同的信息，不能相加为一个“总可信分”：

| 维度 | 回答的问题 | 当前保存方式 |
|---|---|---|
| 静态证据（代码定位 / V1-V4） | 代码结构、SQL、调用或多源关系是否支持这项结论 | 规则证据字段、推演关系 `verification` |
| AI 可信度 | 语义生成器根据静态输入认为该描述有多可靠 | `confidence`，只用于辅助排序 |
| 运行验证（R0-R3） | 这项结论是否在测试或实际环境中被执行和观测 | 独立的 `runtime_evidence` 记录 |
| 人工确认 | 谁认可、修改或废弃了这项结论 | 状态字段与 `confirmations` 审计流水 |

人工确认和运行证据都不会改写 AI 可信度。V 高不代表已经运行过，R 高也不自动代表业务解释已由人确认。

## 2. R 等级定义

| 等级 | 含义 | 允许环境 | 典型证据 |
|---|---|---|---|
| R0 | 没有运行证据；由系统根据“零记录”自动派生 | 无需录入 | — |
| R1 | 已执行测试，并获得支持该结论的结果 | `test` | 单元/集成/API/回归测试名与结果 |
| R2 | 已在受控或预发布环境中观测 | `controlled` / `staging` | Trace、日志条件、测试报告、数据核对 |
| R3 | 已在生产环境中观测或核对 | `production` | 生产 Trace ID、日志查询、业务数据核对单 |

一个目标可以保存多条证据。页面上的当前 R 等级取这些记录中的最高等级；删除误录记录后会重新计算，必要时自动降级。

## 3. 当前覆盖对象

- 业务规则（`rule`）：验证一条校验、计算、状态变化、触发或异常规则确实发生；
- 业务流程（`flow`）：验证一组业务步骤和技术调用在环境中可以形成完整过程；
- 业务推演（`chain`）：验证整条业务主线或对象驱动关系在实际系统中成立。

业务对象和业务域暂不直接挂 R 证据。它们是归类和建模结果，首版优先验证有明确执行语义的规则、流程和推演。

## 4. 数据与生命周期

`runtime_evidence` 的核心字段：

| 字段 | 说明 |
|---|---|
| `scan_id` | 证据所属扫描版本，同时作为项目数据边界 |
| `target_type` / `target_id` | `rule`、`flow` 或 `chain` 及其目标 ID |
| `level` | R1、R2 或 R3；R0 不落库 |
| `evidence_type` | `test`、`trace`、`log`、`reconciliation`、`manual_observation` |
| `environment` | `test`、`controlled`、`staging`、`production` |
| `summary` | 执行内容、输入条件、实际结果和被验证结论 |
| `reference` | 测试名、报告路径、日志条件、Trace ID 或核对单号 |
| `observed_at` / `created_by` / `created_at` | 观测时间、记录人和创建时间 |

语义重跑时，系统只替换机器生成且未确认的规则/流程/推演，并同步删除这些旧目标的运行证据，避免证据悬挂到已经失效的结论。被人工确认或修改而保留的目标，其证据也继续保留。删除整个项目时，运行证据随项目图谱一起清理。

## 5. Web 使用方式

1. 打开“流程与规则”“业务对象与流程”或“业务推演”页面；
2. 在目标详情中查看当前 R0-R3 标签；
3. 点击“添加运行证据”；
4. 选择等级后，页面自动限制到对应环境；
5. 填写证据类型、摘要，并尽量提供可复查的引用和观测时间；
6. 保存后，当前目标立即按已有记录重新计算 R 等级；
7. 误录内容可在本地页面删除，删除后等级自动回算。

规则列表和流程标题只展示聚合等级，详情中展示完整记录。流程接口会批量返回运行证据，避免一个页面为每条流程单独发起请求。

## 6. API

```text
GET    /api/projects/{project_id}/runtime-evidence
GET    /api/projects/{project_id}/runtime-evidence?target_type=rule&target_id=123
POST   /api/projects/{project_id}/runtime-evidence
DELETE /api/projects/{project_id}/runtime-evidence/{evidence_id}
```

创建 R2 证据示例：

```json
{
  "target_type": "flow",
  "target_id": 42,
  "level": "R2",
  "evidence_type": "trace",
  "environment": "staging",
  "summary": "在预发布环境提交订单后依次产生库存预占、采购申请和状态更新，步骤与流程卡片一致。",
  "reference": "trace_id=7f9... / regression-order-approval",
  "observed_at": "2026-08-09T10:30:00+08:00",
  "created_by": "local-user"
}
```

后端会校验目标属于当前项目的最新完成扫描，并强制 R1=test、R2=controlled/staging、R3=production。带时区的观测时间统一转换为 UTC 后存储。

## 7. 导出行为

- 业务规则 Markdown/Word 会显示 AI 可信度、运行等级和人工确认状态，并列出运行证据摘要与引用；
- 规则 Excel 增加静态证据状态、运行验证和人工确认状态列；
- 系统现状说明书显示已纳入文档的运行证据数量和流程运行等级；
- 草稿中的业务推演会显示其运行等级；
- 正式文档不会因为某条未确认规则有 R 证据，就绕过原有人工确认边界把它纳入交付物。

CLI 和 Agent Skills 当前没有运行证据录入命令。它们与 Web 共用 PostgreSQL 时，`c2b docs` 会读取 Web 已录入的证据；独立使用时所有未录入目标自然显示为 R0。

## 8. 当前边界与后续路径

当前已经解决的是“如何用一致的数据结构记录、区分、展示和导出运行事实”，尚未解决的是“如何自动采集事实”。后续可以在不改变 R 模型的前提下增加：

- JUnit/pytest/接口测试报告导入；
- OpenTelemetry Trace 与调用链匹配；
- 日志平台查询结果或 APM 事件导入；
- 生产数据对账任务；
- 证据不可变更、签名、审批和保留策略。

在这些自动化能力落地前，不能把 R3 理解为“系统自动证明正确”；它表示有人录入了生产观测证据，并留下了可复查引用。
