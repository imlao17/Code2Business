## 1. 文档概述

### 1.1 编写目的

本文档用于定义“从源代码中逆向还原业务逻辑”产品的目标、用户、场景、产品形态、核心功能、技术边界、MVP范围、商业模式和后续演进方向。

本产品不是单纯的代码解释工具，而是通过静态分析和 AI 语义理解，将旧系统中的隐性业务知识转换为可阅读、可确认、可追溯、可迁移和可验收的业务资产。当前可人工录入测试、受控环境和生产环境的运行证据；自动运行时分析与数据采集仍是后续增强路径。

当前实现提供两条语义路径：Web 或无人值守 CLI 使用可配置的云端 Provider（OpenAI Compatible 或 Anthropic Native）；在 Codex、Claude Code 等交互式 Agent 中，Skills 可直接使用当前 Agent 的模型，并将带代码证据的结构化结论校验后写入同一业务知识图谱。两条路径都必须经过人工确认，才能进入正式交付物。

### 1.2 产品一句话定义

上传旧系统代码及相关资料，自动还原业务模块、业务流程、业务规则、数据口径和系统接口，形成可用于系统接管、重构、招标和验收的业务知识资产。

## 2. 产品背景

大量传统企业、软件外包项目和政企系统长期存在以下问题：

- 原开发团队离职或无法继续维护；
- 需求文档、设计文档与实际代码不一致；
- 系统可以运行，但没人能完整解释业务逻辑；
- 新团队无法判断修改某段代码会影响哪些功能；
- 系统重构前无法准确盘点现有能力；
- 甲方拿到源码，但无法判断源码是否完整；
- 业务规则分散在代码、数据库、配置、脚本和人工操作中；
- 新旧系统迁移缺少可靠的功能和规则对照基线。

现有代码助手主要解决“代码搜索、代码问答、调用链分析和架构理解”，但通常无法直接形成产品经理、实施顾问和甲方业务人员可使用的业务文档。

因此，产品机会不在于“让 AI 解释代码”，而在于：

> 将源代码中的技术实现，转换为带证据链的业务知识。

## 3. 产品目标

### 3.1 核心目标

1. 自动识别系统中的业务模块和业务对象；
2. 还原关键业务流程和状态流转；
3. 提取校验、计算、权限、状态和自动触发规则；
4. 建立接口、代码、数据表和业务对象之间的关系；
5. 为每个业务结论提供可追溯的代码证据；
6. 支持业务人员对 AI 识别结果进行确认和修订；
7. 自动生成系统现状、重构需求和测试验收文档；
8. 持续跟踪代码变化对业务规则和文档的影响。

### 3.2 非目标

第一阶段不解决以下问题：

- 无源码二进制程序反编译；
- 任意语言、任意技术栈的全覆盖；
- 完全无人参与地恢复全部业务规则；
- 自动完成旧系统到新系统的代码迁移；
- 替代专业安全审计和漏洞扫描；
- 生成可直接上线的重构代码；
- 对 SAP 等封闭商业系统进行完整内部解析。

## 4. 目标用户

### 4.1 企业信息化负责人

主要诉求：

- 盘点现有系统功能；
- 判断系统是否值得继续维护；
- 为系统重构、国产化或招标提供依据；
- 降低对原供应商和原开发人员的依赖。

### 4.2 产品经理与业务分析师

主要诉求：

- 理解系统真实业务规则；
- 将代码实现转换为需求和流程文档；
- 对比现有系统与新系统功能；
- 发现文档和实现不一致的问题。

### 4.3 系统架构师与研发负责人

主要诉求：

- 快速理解陌生代码库；
- 识别模块边界和依赖关系；
- 判断修改影响范围；
- 制定单体拆分、微服务改造和系统重构方案。

### 4.4 软件外包公司与系统集成商

主要诉求：

- 降低接手旧项目的成本；
- 缩短项目调研周期；
- 快速形成项目诊断和报价依据；
- 提高交付文档质量。

### 4.5 实施顾问与测试人员

主要诉求：

- 获取业务流程、规则和数据口径；
- 生成测试场景和验收清单；
- 核对系统实际运行结果；
- 建立业务功能基线。

## 5. 典型使用场景

### 5.1 接手遗留系统

原开发团队已经离职，新团队需要快速了解系统结构、业务流程和关键规则。

交付结果：

- 系统模块地图；
- 接口与调用链；
- 业务规则清单；
- 数据表与业务对象关系；
- 高风险代码和待确认项。

### 5.2 旧系统重构

企业计划将原 Java 单体系统重构为新平台、微服务、低代码平台或国产化系统。

交付结果：

- 现有功能清单；
- 核心业务流程；
- 新旧系统功能对照；
- 数据迁移对象；
- 接口迁移清单；
- 重构需求规格；
- 测试验收基线。

### 5.3 外包系统验收

甲方已拿到源码，但无法确认交付范围与合同需求是否一致。

交付结果：

- 已实现功能；
- 未发现实现的需求；
- 接口和数据库清单；
- 权限和状态规则；
- 文档与代码不一致项；
- 验收测试清单。

### 5.4 业务规则治理

系统长期迭代后，同一业务规则在不同模块中存在重复、冲突或不一致实现。

交付结果：

- 重复规则；
- 冲突规则；
- 规则来源；
- 影响模块；
- 建议统一方案。

### 5.5 持续业务文档同步

每次代码发布后重新扫描，对比业务能力和规则变化。

交付结果：

- 新增业务规则；
- 修改业务流程；
- 删除或废弃接口；
- 数据结构变化；
- 文档与代码差异；
- 潜在回归风险。

- 为接管、重构、招标和验收建立可靠基线。

## 7. 产品形态

推荐采用：

> 本地扫描器 + Web 业务分析工作台 + AI 问答助手

### 7.1 本地扫描器

部署在客户电脑、服务器或企业内网中。

主要职责：

- 拉取或读取 Git 代码仓库；
- 解析源码、SQL、配置和接口定义；
- 生成代码结构图谱；
- 提取调用链、数据流和数据访问关系；
- 对敏感代码进行本地处理；
- 将结构化分析结果上传到平台；
- 支持完全私有化部署。

### 7.2 Web 业务分析工作台

作为产品主界面，面向产品经理、架构师、实施顾问和甲方人员。

主要能力：

- 系统全景；
- 业务地图；
- 流程还原；
- 规则中心；
- 数据血缘；
- 接口分析；
- 文档生成；
- 人工确认；
- 版本对比。

### 7.3 AI 问答助手

AI 问答不是独立产品，而是业务知识图谱的自然语言入口。

示例问题：

- 采购订单审批通过后会发生什么？
- 库存数量是在哪些场景下更新的？
- 应收账款是如何生成的？
- 合同已收款金额是怎么计算的？
- 修改订单状态字段会影响哪些模块？
- 哪些接口会写入库存表？
- 当前系统有哪些自动生成应付账款的逻辑？

回答必须包含：

- 业务结论；
- 触发条件；
- 处理步骤；
- 状态变化；
- 数据变化；
- 影响范围；
- 代码证据；
- 可信度；
- 待确认项。

## 9. 业务知识模型

### 9.1 核心实体

系统内部需建立以下业务知识对象：

1. 业务域；
2. 业务模块；
3. 业务对象；
4. 业务动作；
5. 业务流程；
6. 业务规则；
7. 业务状态；
8. 数据对象；
9. 数据字段；
10. 系统接口；
11. 外部系统；
12. 代码对象；
13. 证据；
14. 待确认问题；
15. 文档资产。

### 9.2 关系示例

```text
销售合同
  ├─ 包含 → 合同明细
  ├─ 关联 → 客户档案
  ├─ 生成 → 收款计划
  ├─ 触发 → 应收账款
  ├─ 约束 → 出库数量
  ├─ 更新 → 合同执行金额
  └─ 被实现于 → ContractService
```

### 9.3 技术对象到业务对象映射

技术对象：

```text
PurchaseOrderService.approve()
```

业务语义：

```text
业务动作：采购订单审批通过
触发条件：审批结果为同意
前置状态：审批中
后置状态：已审批
产生数据：采购执行记录、应付账款
影响对象：采购订单、供应商、项目
```

## 10.6 业务规则中心

### 功能说明

自动识别并管理代码中的业务规则。

### 规则类型

#### 校验规则

示例：

- 入库数量不得大于采购订单未入库数量；
- 付款金额不得大于应付未付金额；
- 合同结束日期不得早于开始日期；
- 库存不足时禁止出库。

#### 计算规则

示例：

- 未付款金额 = 应付金额 - 已付款金额；
- 含税金额 = 不含税金额 ×（1 + 税率）；
- 可执行数量 = 合同数量 - 已执行数量。

#### 状态规则

示例：

```text
待提交 → 审批中 → 已审批 → 执行中 → 已完成
```

#### 权限规则

示例：

- 只有采购负责人可以修改待提交订单；
- 审批中的订单不可删除；
- 财务人员可以执行付款核销。

#### 自动触发规则

示例：

- 订单审批通过后生成应付账款；
- 入库完成后更新库存；
- 库存低于安全库存时生成预警。

#### 异常规则

示例：

- 重复审批时抛出异常；
- 未找到供应商时中止处理；
- 外部接口调用失败时进入补偿队列。

### 规则管理状态

- AI 识别；
- 待确认；
- 已确认；
- 已修改；
- 已废弃；
- 存在冲突。

## 10.7 业务逻辑卡片

### 功能说明

将每条业务逻辑作为平台中的最小知识单元。

### 卡片字段

| 字段 | 说明 |
|---|---|
| 逻辑名称 | 业务动作或规则名称 |
| 所属业务域 | 所属业务范围 |
| 所属模块 | 所属功能模块 |
| 触发方式 | 页面、API、消息、定时任务等 |
| 前置条件 | 逻辑执行前必须满足的条件 |
| 输入数据 | 参与处理的数据 |
| 处理逻辑 | 业务执行过程 |
| 状态变化 | 业务状态前后变化 |
| 数据变化 | 新增、修改、删除的数据 |
| 后续动作 | 继续触发的处理 |
| 异常处理 | 异常和补偿机制 |
| 影响范围 | 受影响的模块和对象 |
| 代码证据 | 文件、方法和代码行 |
| 数据证据 | 表、字段和 SQL |
| 运行证据 | 调用链和日志 |
| 可信度 | AI 对结论的可信度 |
| 确认状态 | 待确认、已确认等 |

## 11. 证据链与可信度机制

### 11.1 证据类型

每一个业务结论可以关联以下证据：

- 源代码；
- 方法调用；
- 控制流；
- 数据流；
- SQL；
- 数据库结构；
- 配置文件；
- API 文档；
- 单元测试；
- 集成测试；
- 运行调用链；
- 日志；
- Git 提交；
- 原有需求文档；
- 人工确认记录。

### 11.2 可信度计算因素

正向因素：

- 静态调用链完整；
- 数据流证据完整；
- 存在运行时调用证据；
- 存在自动化测试；
- 多处实现结果一致；
- 已被业务人员确认。

负向因素：

- 存在反射调用；
- 存在动态 SQL；
- 外部系统不可见；
- 配置缺失；
- 调用链中断；
- 多处逻辑冲突；
- 仅依靠命名推断。

### 11.3 可信度展示

建议分为：

- 高可信：90%—100%；
- 较高可信：75%—89%；
- 中等可信：50%—74%；
- 低可信：低于 50%。

可信度不代表绝对正确，只代表当前证据完整程度。

## 12. 技术方案原则

### 12.1 不采用纯大模型方案

禁止将整个代码库直接交给大模型进行自由总结。

原因：

- 上下文不完整；
- 跨文件调用容易遗漏；
- 结论不可复现；
- 动态调用容易误判；
- 无法形成稳定证据链；
- 不同提问可能得到不同答案。

### 12.2 四层分析架构

#### 第一层：确定性代码分析

负责：

- AST；
- 类、方法、变量；
- 调用关系；
- 控制流；
- 数据流；
- SQL 读写；
- API 入口；
- 消息入口；
- 定时任务；
- 前端路由；
- 状态枚举。

#### 第二层：业务语义分析

由 AI 负责：

- 识别业务对象；
- 归纳业务模块；
- 提取业务动作；
- 生成规则描述；
- 识别状态变化；
- 识别相似和冲突规则；
- 将技术流程转换成业务流程。

#### 第三层：运行时验证

接入：

- OpenTelemetry；
- API 日志；
- SQL 日志；
- MQ 日志；
- 定时任务日志；
- 测试执行结果。

#### 第四层：人工确认

用户可以：

- 修改业务名称；
- 调整流程；
- 补充业务说明；
- 确认规则；
- 标记错误推断；
- 合并重复规则；
- 添加缺失关系；
- 建立正式业务基线。

## 21. 主要风险

### 21.1 代码不等于完整业务

部分规则可能存在于：

- 人工操作；
- Excel；
- 数据库手工修改；
- 运维脚本；
- 第三方系统；
- 配置中心；
- 口头约定。

解决方案：

为每条结论标记来源：

- 代码中已实现；
- 运行中已验证；
- 文档中有描述；
- 业务人员已确认；
- 尚未发现证据。

### 21.2 动态调用难以还原

反射、动态 SQL、脚本和消息队列可能导致静态调用链不完整。

解决方案：

- 接入运行时调用链；
- 标记中断节点；
- 允许人工补链；
- 可信度降级。

### 21.3 业务流程与技术调用混淆

技术调用顺序不等于业务流程。

解决方案：

- 同时保留业务层和技术层；
- 允许业务人员合并技术步骤；
- 使用业务动作作为流程节点；
- 技术细节按需展开。

### 21.4 AI 生成错误

AI 可能对业务名称和规则含义产生错误推断。

解决方案：

- 所有结论必须有证据；
- 推测内容必须单独标记；
- 允许人工确认；
- 禁止无证据结论进入正式文档。

### 21.5 客户源码安全顾虑

客户可能拒绝将源码上传到云端。

解决方案：

- 本地扫描；
- 私有化部署；
- 源码不出内网；
- 仅上传图谱和摘要；
- 支持离线模型。
- 支持 Agent Native：当前 Agent 仅基于本地源码和扫描证据生成结论，导入时验证文件、方法和行号；无需为该路径额外配置云端 Key。

4. 是否需要完全离线部署？
5. 是否接入运行日志和 OpenTelemetry？
6. 首批用户是产品经理、架构师还是实施顾问？
7. 文档生成优先支持哪些模板？
8. 是否将系统重构诊断作为首个销售产品？
9. 是否需要支持前端页面与后端接口自动映射？
10. 是否需要与 Jira、禅道、GitLab 或 GitHub 集成？

---

## 24. 最终结论

这个产品的核心不是“让 AI 解释代码”，而是：

> 把旧系统中没人能完整说清楚的业务知识，转换成企业可以继续使用、确认、迁移、验收和治理的资产。

第一版应聚焦 Java 企业管理系统，优先验证：

1. 系统模块及对象地图；
2. 从接口到数据库的业务链路；
3. 带代码证据的业务规则卡片。

只要这三项能够达到“产品经理稍作修改即可向客户交付”的程度，产品方向就具备成立基础。
