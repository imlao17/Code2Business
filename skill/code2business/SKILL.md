# Code2Business 最低参考版

把旧代码库还原成业务资产。工作流固定为 **探测 → 分片 → 逐片分析 → 资产产出 → 汇总文档**，五步都必须执行。

## 第一步：探测规模

```bash
python3 <skill>/scripts/probe.py <code_root> --output <workdir>
```

- `<workdir>` 为本次分析的工作目录（新建，如 `./analysis/<项目名>-<日期>`）
- 产出 `scale_report.json`（规模/语言/模块分布/编码/巨型文件/疑似历史版本）+ `shard_plan.json`（分片方案）
- 向用户展示规模报告摘要（档位、总行数、Top 模块、编码、历史版本提示），**先让用户确认再继续**
- 这是本地探测报告，不会创建 c2b 数据库内的 `project_id` / `scan_id`

档位：S≤10万 / M≤100万 / L≤200万 / XL>200万。S/M 档不切片，直接进入第三步；L/XL 档按 `shard_plan.json` 的 shards 逐片分析。

## 第二步：提取入口（辅助定位）

```bash
python3 <skill>/scripts/extract_entries.py <code_root> --output <workdir>
```

产出 `entries.csv`（batch/api/schedule/mq/gui 四类入口 + 文件:行）。批处理系统重点看 `batch` 类（main 方法）。

## 第三步：逐片语义分析（核心，模型直读代码）

对每片（或全量，视档位）：

1. 按 `scale_report.json` 的模块行数**降序**处理模块，先大后小；
2. 每个模块：先读入口文件（`*_L.java` / main / Controller / 事件类），再读核心业务类；
3. **识别规则**（参考 `references/output-format.md` 的规则特征清单）；
4. 产出规则卡片，写 `04-规则卡片.md`。

### 读取代码的硬性约束

- **证据强制**：每条结论必须带 `文件:行号` 证据，无证据的推断只能进"待确认项"；
- **防幻觉**：只基于实际读到的代码；业务含义模糊时写"疑似"，不编造业务名称；
- **历史版本文件**：文件名含 `_old`/`_20130206`/`履歴`/`移行`/`不要` 等的文件标记为"历史版本"（探测报告有统计），默认只读无后缀主文件，历史版本不深读但注明；
- **非 UTF-8 编码**（探测报告提示 shift_jis 等）：读取乱码时先转码再读：
  ```bash
  iconv -f SHIFT-JIS -t UTF-8 "文件" > /tmp/转码.java   # 或 python3 -c "..."
  ```
- **大文件分段**：>5000 行的文件用 Read 的 offset/limit 分段读，不要一次全读；
- **未覆盖声明**：没读到的模块/文件在输出中明确标注"未覆盖"，不得假装已分析。

### 优先级（XL 档必做）

- 先批处理入口（`*_L.java`）和主文件，再扩展类；
- 每片完成后记录"本片已覆盖/未覆盖"清单，供用户决定是否深挖。

## 第四步：资产产出

在 `<workdir>/output/` 下写：

| 文件 | 内容 |
|---|---|
| `01-规模报告.md` | 探测结果整理（档位/行数/模块分布/编码/历史版本提示） |
| `02-模块地图.md` | 每个模块：职责、入口、依赖关系（读代码得出）、数据表线索 |
| `03-入口清单.md` | 按类型分组的入口清单（batch/api/schedule/mq）+ 入口职责 |
| `04-规则卡片.md` | 逐条规则卡片（模板见 references/output-format.md） |
| `05-待确认项.md` | 所有无法确认的推断、未覆盖模块、存疑点 |
| `06-系统现状说明书.md` | 面向客户交付的汇总文档（模板见 references/output-format.md） |
| `data/` | 复制 scale_report.json、shard_plan.json、entries.csv |

## 第五步：汇总

- 向用户交付：规模报告摘要 + 各资产文件路径；
- 明确说明**哪些模块已覆盖、哪些未覆盖、哪些待确认**；
- 提醒：本版本是参考实现，自动化深度（调用图/血缘）见项目内 `mvp-tech-solution.md`。
